- **Multi-agent notification support**: Telegram/Discord now notify for Claude Code, Codex CLI, Gemini CLI, and Aider
- **Terminal lifecycle tracking**: Ghost terminal cache, async destroy with proper cleanup, enhanced message formatting
- **Telegram command router**: Multi-agent support with chat mode and pending state management

## The Brutal Truth

This release feels like we finally got serious about **product quality**. For months, the notification system was Claude-only and the release process was fragile—relying on manual GitHub action triggers and script guesswork. Shipping 3.1.1 means we now have:

- **5 different agent types** notified through the same pipeline (Claude, Codex, Gemini, Aider + our fallback)
- **Reproducible releases** that can be previewed locally before GitHub touches them
- **Three critical security gaps closed** that nobody complained about yet, but would have been disasters in production

The frustrating part? We should have fixed the security issues in 3.1.0. The IPC handlers had path traversal risk in IMAGE_OPEN, YOLO_MODE_SET could write arbitrary JSON to unvalidated projects, and the CI workflow was vulnerable to shell injection via `inputs.tag`. These weren't complex to fix (15 lines total), but they sat unsigned until integration testing caught them.

What makes this ship feel *solid* though: 330 tests pass, zero flaky failures, and the terminal async cleanup actually works now. The "ghost terminal" problem (exited terminals staying in memory) is genuinely fixed with proper event lifecycle tracking.

### Terminal Lifecycle & Ghost Terminal Cache

**Files changed:** 8 | **Lines:** +156 / -89

The problem: Terminal processes exit, but terminal state lingered in memory. Notification callbacks would fail because terminal lookups happened *after* destroy completed.

Solution:
- Cache exited terminal metadata before async destroy (`preserveExitedTerminalState`)
- Async `destroyAllAsync()` with proper cleanup sequence (notify → clear listeners → kill process → remove from cache)
- Terminal lookup checks both active and exited cache before rejecting callbacks
- Cache cleanup happens after all notification processing completes

Test coverage: 40 tests for TerminalManager, including explicit async destroy race condition checks.

### Security Fixes Applied Before Ship

**Commit:** 03f3c20 | **Lines:** +14 / -2

1. **IMAGE_OPEN path guard** (IPC Handler)
   - Risk: No validation on file path, could read arbitrary files
   - Fix: Restrict to `multiClaude-screenshots/` subdirectory (matches IMAGE_DELETE/IMAGE_READ_BASE64)
   - Status: Blocking path traversal attempts

2. **YOLO_MODE_SET validation** (IPC Handler)
   - Risk: Could write `.claude/settings.local.json` to any project in store
   - Fix: Validate projectPath exists in project store before allowing write
   - Status: Blocks unauthorized project config injection

3. **CI Workflow tag injection** (Release Workflow)
   - Risk: `inputs.tag` passed directly to shell, allows command injection
   - Fix: Use env var indirection + semver format validation
   - Status: Prevents arbitrary code execution during release

These were not high-profile exploits, but they were genuine vulnerabilities that would have enabled:
- Reading user files (screenshots, docs)
- Modifying project configs without authorization
- Breaking CI/CD pipeline security

## What We Tried

### Multi-Agent Detection Approach

**Rejected:** Per-agent SDK integration (Codex SDK, Gemini SDK integration)
- Reason: Out of scope, requires external dependencies, tightly couples to specific versions

**Rejected:** Process monitoring (attach to all child processes)
- Reason: Overly complex, race conditions with process trees, hard to implement reliably

**Accepted:** Exit-code detection + binary name matching
- Simple, observable from terminal manager, doesn't require SDK knowledge
- Trades some richness for reliability

### Terminal Lifecycle

**Rejected:** Synchronous destroy
- Reason: Blocked notification delivery if destroy took too long

**Rejected:** Fire-and-forget destroy (no cleanup guarantee)
- Reason: Eventually terminal cache fills with dead processes, memory leak

**Accepted:** Async destroy with explicit cleanup sequence
- Ensures notifications complete before removing cache
- Proper event sequencing prevents race conditions
- Tests verify all edge cases

### Release Process

**Rejected:** GitHub Actions only (like 3.1.0)
- Reason: Can't preview locally, requires manual trigger, error messages hidden in logs

**Accepted:** Local preview + CI execute split
- Developers can `npm run release:preview` to see exactly what will ship
- CI never decides—only executes validated decisions
- All validation in code, testable offline

## Root Cause Analysis

### Why Security Issues Existed Until Now

**Root cause:** Security hardening was never part of the feature checklist. The notification/terminal work focused on functionality; security was "we'll handle it later."

What should have happened:
1. During initial IPC handler design → security review for path traversal
2. During YOLO_MODE_SET implementation → validate projectPath parameter
3. During CI workflow setup → review shell expansion, use env var indirection from day one

**Contributing factor:** No precommit security check (no `npm audit`, no static analysis for IPC inputs). Tests covered happy paths, not threat models.

### Why Terminal Lifecycle Was Hard

**Root cause:** Terminal state was never designed as a "lifecycle" with distinct phases (active → exiting → exited → dead). Code treated "exited" as "immediately delete," which broke async notification callbacks.

The ah-ha moment: Realizing the terminal manager shouldn't own the "destroy decision"—notifications should. Only after notification handlers complete should the terminal actually be removed.

## Lessons Learned

### 1. Security Must Be In Code, Not Backlog
We got lucky the IPC issues didn't get exploited. The fix took 15 minutes once we knew what to check. The failure was **never checking in the first place.**

Future approach:
- Security review checklist for IPC handlers (path validation, project ownership checks)
- Every script that takes user input gets validation before shell expansion
- `npm audit` in precommit (blocks if critical/high)

### 2. Async Cleanup Requires Explicit State Machines
The terminal lifecycle problem kept popping up because we were reasoning about state ad-hoc. Once we drew the explicit states (active → exiting → exited → dead) and sequenced cleanup properly, the race conditions disappeared.

This applies anywhere we have resource cleanup. Be explicit about state transitions, not implicit about "the destroy will happen eventually."

### 3. Release Tooling Pays for Itself Immediately
Built the release scripts to help debug CI issues. Immediately discovered they prevent human error (wrong version format, duplicate releases, incomplete changelog). 

The "npm run release:preview" command is *probably* worth more than the feature code itself because developers can validate before pushing.

### 4. Tests Should Cover Threat Models, Not Just Happy Paths
The security issues weren't caught by existing tests because tests only checked "does the feature work?" not "can this be abused?"

For IPC: Test with malicious paths (`../../../etc/passwd`), wrong project IDs
For versioning: Test invalid semver, injection attempts
For CLI: Test missing validation, edge cases
